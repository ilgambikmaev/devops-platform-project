# Observability: выбор стека и обоснование

## Обзор

Платформа использует связку **Loki + Prometheus + Tempo + Grafana + Alertmanager**
для покрытия всех трёх столпов наблюдаемости (логи, метрики, трейсы) через единую
точку визуализации.

## Логи: Loki vs VictoriaLogs vs ELK vs SigNoz

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **Loki** (выбран) | Индексирует только метаданные (labels), не полнотекстовый индекс — на порядок легче по RAM/диску; нативная интеграция с Grafana; Promtail как лёгкий агент-сборщик | Полнотекстовый поиск медленнее, чем в Elasticsearch | ✅ |
| Elasticsearch/Logstash/Kibana | Мощный полнотекстовый поиск, зрелая экосистема | Тяжёлый (JVM, от 1-2 ГБ RAM только на один узел ES), избыточен для объёма логов учебного стенда | ❌ |
| VictoriaLogs | Тоже легковесный, хорошая производительность | Моложе и менее распространён в продакшене, меньше готовых интеграций с остальным стеком | ❌ |
| SigNoz | All-in-one (логи+метрики+трейсы), удобен для старта | Завязан на ClickHouse — ещё одна тяжёлая СУБД в кластере | ❌ |

**Решение:** Loki — минимальный footprint при ограниченных ресурсах локальной машины,
при этом полностью логически совместим с остальным Grafana-стеком.

## Метрики: Prometheus vs VictoriaMetrics vs InfluxDB

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **Prometheus** (выбран) | Индустриальный стандарт для Kubernetes; `kube-prometheus-stack` даёт готовый набор алертов и дашбордов "из коробки" (etcd, kubelet, API-сервер и т.д.), экономя время на написание правил с нуля | При очень большом объёме временных рядов требует доп. решения (Thanos/Cortex) для долгосрочного хранения — не актуально для учебного стенда | ✅ |
| VictoriaMetrics | Меньше потребление RAM/CPU на больших объёмах, drop-in совместим с Prometheus API | Меньше готовых community-дашбордов и alert-правил под конкретно k8s, пришлось бы переносить/адаптировать | ❌ |
| InfluxDB | Хорош для time-series вне k8s-контекста (IoT, метрики приложений) | Не специализирован под Kubernetes-мир, нет аналога kube-state-metrics интеграции | ❌ |

**Решение:** Prometheus — готовый экосистемный набор правил и дашбордов существенно
сократил время настройки; масштаб данного стенда не требует VictoriaMetrics-уровня
оптимизации по ресурсам хранения.

## Трейсы: Tempo vs Jaeger vs Uptrace

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **Tempo** (выбран) | Нативная интеграция с Grafana (переход из трейса в логи/метрики одним кликом через exemplars); не требует отдельной БД для индекса — хранит блоки объектным способом | Поиск по тегам менее гибкий, чем в Jaeger UI | ✅ |
| Jaeger | Зрелый, удобный собственный UI, широко известен | Требует отдельного backend-хранилища (Elasticsearch/Cassandra) для продакшен-объёмов — лишний тяжёлый компонент | ❌ |
| Uptrace | Совмещает трейсы+метрики+логи на ClickHouse | Ещё одна тяжёлая СУБД (ClickHouse) в уже нагруженном кластере | ❌ |

**Решение:** Tempo — единственный вариант из трёх, не требующий отдельной СУБД
для хранения индекса, и дающий наиболее плотную интеграцию с уже выбранными
Loki и Prometheus через общий Grafana UI.

## Инструментация приложений

Сервис `demo-service` инструментирован через **OpenTelemetry SDK** (auto-instrumentation
для Flask), с прямой отправкой спанов в Tempo по протоколу OTLP/HTTP — без
промежуточного OpenTelemetry Collector, чтобы не добавлять ещё один компонент
в и так плотный по ресурсам кластер. В продакшен-развёртывании между приложениями
и Tempo обычно ставится OTel Collector для батчинга, семплирования и маршрутизации
в несколько бэкендов одновременно.

## Визуализация и алертинг

**Grafana** — единая точка входа для всех трёх источников данных (Loki datasource,
Prometheus datasource, Tempo datasource), что позволяет коррелировать логи, метрики
и трейсы одного инцидента в одном интерфейсе.

**Alertmanager** — обрабатывает алерты от Prometheus. Используется готовый набор
правил из `kube-prometheus-stack` (etcd, kube-apiserver, kubelet, ресурсы подов,
доступность control-plane), покрывающий инфраструктурный уровень платформы без
необходимости писать эти правила вручную.

## Ограничения текущего развёртывания

- Все компоненты стека развёрнуты в single-instance конфигурации (без репликации) —
  осознанное решение из-за ограниченных ресурсов локальной машины для разработки.
  В продакшене Prometheus/Loki/Tempo разворачиваются в кластерном режиме
  (Prometheus + Thanos, Loki в microservices mode, Tempo с распределённым хранилищем).
- Полная инструментация трейсинга сделана только для `demo-service`, как
  демонстрация работающего механизма end-to-end. `order-service` и
  `notification-service` используют тот же паттерн подключения и могут быть
  инструментированы аналогично.
